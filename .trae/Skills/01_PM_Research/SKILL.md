# 产品调研与优先级

产品经理的价值不在于想出功能，在于**用证据决定做什么、不做什么**。

## 一、竞品分析

不要做"功能列表打勾"。按这个结构才有用：

| 维度 | 看什么 |
|:---|:---|
| 定位 | 一句话说清它给谁解决什么 |
| 核心路径 | 从进入到达成目标的步数，截图对比 |
| 差异点 | 它做了什么别人没做的，为什么 |
| 商业模式 | 谁付钱，付多少，怎么收 |
| 用户口碑 | 应用商店差评 / 小红书 / 知乎里真实抱怨 |
| 我们的机会 | 它做不好但我们可以做的 |

**关键动作**：注册并用一遍。竞品分析靠看的结论都是错的。

输出格式：先给结论（3 条以内），再给对比，最后给"所以我们该做什么"。

## 二、用户调研

**访谈提纲模板（30 分钟）**

1. 你最近一次做 X 是什么时候？（问具体行为，不问态度）
2. 当时怎么做的？用了哪些工具？
3. 哪一步最麻烦？为什么？
4. 为此你付出过什么代价（时间/钱/情绪）？
5. 试过别的办法吗？为什么放弃了？

规则：

- 问**过去发生了什么**，不问"你会不会用"
- 不要引导："是不是觉得很不方便？"→"当时是什么感受？"
- 5 个用户能发现大部分共性问题，不要为了样本量拖延
- 访谈记录保留原话，原话是最好的需求来源

## 三、需求优先级

**RICE**

```
得分 = (触达人数 × 影响程度 × 信心) / 投入
```

- 触达：一个周期内影响多少用户
- 影响：3 巨大 / 2 高 / 1 中 / 0.5 低 / 0.25 微小
- 信心：100% / 80% / 50%
- 投入：人周

**KANO**

| 类型 | 特征 | 策略 |
|:---|:---|:---|
| 必备 | 没有会被骂，有了不加分 | 做到及格，别投入过多 |
| 期望 | 越多越满意，线性关系 | 主要竞争区 |
| 兴奋 | 没有不失望，有了惊喜 | 差异化来源 |
| 无差异 | 做不做都一样 | 直接砍 |

**砍需求的话术**：不是"这个做不了"，而是"这个的投入相当于 A+B，而 A+B 的触达是它的 3 倍，我们先做哪个？"

## 四、指标体系

先定**北极星指标**（一个能代表用户获得价值的数），再拆支撑指标。

```
北极星：周活跃完成作业的学生数
├── 获取：新注册 → 首次完成作业的转化率
├── 留存：次周回访率
├── 体验：任务完成时长、失败率
└── 传播：邀请数 / 分享数
```

规则：

- 指标必须是**能变的**（不能是"用户满意度"这种不可直接操作的）
- 一个功能最多 3 个指标，多了就没重点
- 定指标时同时定"降到多少算失败"

## 五、埋点设计

最小埋点表：

| 字段 | 说明 |
|:---|:---|
| 事件名 | 动词_名词，如 `task_complete` |
| 触发时机 | 成功回调后，不是点击时 |
| 属性 | 关键上下文，如任务类型、来源页 |
| 用户标识 | 匿名 ID + 登录 ID 双写 |

常见错误：

- 点击即上报 → 实际没成功也算，数据虚高
- 事件名不统一（`clickBtn` / `button_click` 混用）
- 没有版本号，改版后新旧数据混在一起
- 埋了不看的点，浪费开发时间

## 六、输出约定

调研结论必须包含：

1. 一句话结论
2. 证据：原话、数据、截图
3. 覆盖范围与局限（访谈了几个人，是否只覆盖某一类用户）
4. 建议动作与优先级
5. 明确标注哪些是推测

不要写"用户普遍认为""大家都很需要"这类没有出处的判断。
