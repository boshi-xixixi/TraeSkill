# 数据分析与可视化

数据分析的产出不是代码，是**一个能站得住的结论**。代码只是中间产物。

## 一、拿到数据的前 10 分钟

不要立刻 `df.head()` 然后开始写图。按这个顺序过一遍：

```python
df.shape                    # 多少行多少列
df.dtypes                   # 每列什么类型
df.isna().sum()             # 缺失分布，不看总数看分布
df.duplicated().sum()       # 重复行
df.describe(include='all')  # 数值看分布，类别看频次
```

然后回答三个问题：

1. **一行代表什么？**（订单？用户？用户-天？）——粒度错，后面全错
2. **主键是什么？** 有没有重复计数
3. **哪几列是算出来的？**（如 GMV = 数量 × 单价）——别把派生列当独立变量

## 二、清洗顺序

顺序错了会白干，按这个来：

1. **类型修正**：数字被读成字符串（`"1,234"`）、日期被读成 object
2. **去重**：先确认口径再删，宁可标记不删
3. **缺失处理**：先分类，再决定
   - 真缺失（没采集到）→ 删除或插补
   - 逻辑不适用（未婚者的配偶姓名）→ 保留为空，不要填 0
4. **异常值**：先看是否真实（大客户、促销日），不要无脑 3σ
5. **口径统一**：时间区间、货币单位、区域编码
6. **派生列**：计算列要有清晰命名和注释

> 清洗必须留痕：删了多少行、为什么删，写进注释或输出日志。否则结论无法复现。

## 三、EDA 检查清单

- 单变量：数值看分布形状（直方图 + 分位数），类别看长尾（`value_counts()` 前 20）
- 双变量：连续 × 连续看散点，连续 × 类别看分组箱线，类别 × 类别看交叉表
- 时间：先看趋势再看周期，注意**口径变化**（改版、活动、数据源切换）造成的断点
- 分组：任何"平均值"都问一句"分群之后还成立吗"（辛普森悖论）

## 四、图表选型

| 想表达 | 用什么 | 不要用 |
|:---|:---|:---|
| 随时间变化 | 折线 | 饼图、3D 柱 |
| 类别比较 | 条形（横向，按值排序） | 饼图（超过 4 类） |
| 分布 | 直方图、箱线、小提琴 | 只有均值 |
| 两个变量关系 | 散点 + 趋势线 | 双 Y 轴折线 |
| 构成 | 堆叠条形、百分比堆叠 | 饼图超过 5 块 |
| 相关矩阵 | 热力图 | 3D 曲面 |

通用规则：

- 纵轴从 0 开始（折线可例外，但要在图注里说明）
- 颜色不要超过 6 种，且不要只靠颜色区分（考虑色盲）
- 标题写结论，不写"图 1 销售额变化"，写"Q3 销售额环比下降 12%"
- 中文图表记得设置字体，否则方块乱码

## 五、常见统计陷阱

| 陷阱 | 表现 | 怎么破 |
|:---|:---|:---|
| 辛普森悖论 | 整体趋势和分群趋势相反 | 拆开看每一群 |
| 幸存者偏差 | 只统计留下来的样本 | 问"没进来的去哪了" |
| 均值欺骗 | 收入均值被少数极端值拉高 | 同时给中位数和分位数 |
| 相关当因果 | "A 涨 B 也涨，所以 A 导致 B" | 找反例，找第三变量 |
| 口径漂移 | 前后期统计标准不同 | 对齐口径再比较 |
| 小样本 | 3 个用户说好就下结论 | 给出样本量和置信区间 |

## 六、输出结构

分析结论按这个骨架写，比堆图有用：

1. **一句话结论**（先说结果）
2. **数据范围**：时间、来源、样本量、已知局限
3. **关键发现**：3 条以内，每条配一张图
4. **反直觉的点**：如果有，单独拎出来
5. **建议动作**：可执行、有优先级
6. **不确定的地方**：明确标注是推测不是结论

## 七、性能与工程

- 大文件用 `pd.read_csv(..., chunksize=)` 或 `dtype` 指定类型
- 避免 `df.apply` 逐行，优先向量化
- 反复用的中间结果存 parquet，不要每次重算
- 分析脚本要能被别人重跑：固定随机种子，路径用变量

## 八、写作要求

- 数字带单位和口径（"客单价 128 元（含运费）"而不是"128"）
- 百分比变化说清基数（"增长 200%" 和 "从 1 到 3" 差很远）
- 不写"显著"，除非真的做了显著性检验
- 图表必须能被单独看懂：标题、坐标轴、单位、数据来源

## 九、对账与校验

结论交出去之前，按这个顺序过一遍。核心原则：**机器判事实，人判品味**——行数守恒、总和守恒、图有没有出框，这些能自动验；这个分析有没有意义，只能人来判。

**1. 先当 bug，再当发现**
Twyman 定律：看起来异常的数字，通常是错的。增长 300%、转化率翻倍、某渠道突然登顶，先排查采集、去重、口径，排除之后再当成结论。

**2. 表里的"合计"行是免费的校验和**
多数工具会把它当噪音滤掉，但那通常是原表作者用公式算出来的真值。清洗后的明细求和必须能对上它，对不上就说明有一方错了，两种可能都要说出来。

**3. 没有合计行时，"我验过了"和"我没东西可验"是两回事**
系统导出、API 返回、日志类数据永远不会有合计行。默认动作是换一条独立代码路径重算（换个库、换种读法、重写同一套规则），两条路对不上就有一方错了。做不到就明写"本次结果没有独立校验来源"，不要混在一堆说明里带过。

**4. 加总为 100% 不代表覆盖你以为的范围**
一张份额表逐月加总恰好为 1，看起来口径很严，但那个 1 可能只含五个玩家里的两个——"份额"悄悄变成了"这两家之间的相对比例"。验完加总，再点名：这个池子里有谁、谁不在、为什么不在。

**5. 派生列必须动手验，不能看列名**
有一列叫"评委直觉分"，和五维均分相关系数 0.944，看上去五维没有信息量。实际那列就是五维均分的四舍五入值，0.944 只是 `corr(x, round(x))` 的算术常数。试一次 round、试一次比值、试一次差，一分钟能挡住一整条建立在恒等式上的结论。

**6. 别用自己选的窗口证自己想要的结论**
换一个时间窗口再算一遍，结论还在才算数。

**7. 口径不一样的数不能进同一个 sum()**
多币种混着求均值、毛额净额混着加、中位数列和百分比列一起丢进合计。加之前问一句：这一列里每个数的分母都一样吗？

**8. 不要自己审自己**
前七条你完全可能一边知道、一边照犯，因为自查时带着"它应该成立"的先验。交付前另找一个不参与创作的人（或另一个 agent）来拆台，重点验机器验不了的那几项：列名是不是它字面的意思、正文里手打的数字和数据对不对得上、时间窗口是不是挑出来的。

## 十、闸门能验什么、验不了什么

| 闸门能验 | 闸门验不了 |
|---|---|
| 行数守恒、总和守恒 | 这个数是不是用对了变量算的 |
| 声称值 vs 明细求和 | 两个数能不能相减（比率 − 回归系数） |
| 图有没有画出框、叠字 | 结论有没有超出置信区间 |
| 字体、表头重复 | 列名是不是它字面的意思 |

一份内部对账分毫不差、行数与金额全部恒等的报告，可以整体错掉一个财年——只要那一列的名称不是它字面的意思。**内部一致性证明不了列语义。**
